Shell & Subprocess

“Execution Providers”

Key Insight:

Shell execution is a capability — local, remote, or sandboxed providers all share one interface.

Shell execution is a capability with local, remote, or sandboxed providers all sharing one interface. This allows the same tools to work in different environments.

Architecture Flow

Provider Abstraction

The shell interface abstracts execution environment. The same 'bash' tool works whether executing locally, remotely, or in a sandbox — only the provider changes.

Sandbox Integration

Sandbox providers can restrict filesystem access, network calls, and process spawning. The tool code doesn't change — security is enforced at the provider level.

Design Decisions

Filesystem and subprocess providers share one execution world, so pointing them at a remote sandbox moves everything.

Security is enforced at the provider level, not in tool code, enabling consistent policy across all tools.

Comparison: Claude Code

DeepSeek Harness has pluggable shell providers; Claude Code has fixed local execution.

Deep Dive: Design Decisions

SKILL.md as the Unit of Knowledge

Each skill is a single SKILL.md file with YAML frontmatter (name, description) and markdown body. This is the simplest possible format that's both human-readable and machine-parseable.

Alternatives: A structured format like JSON or YAML-only would be machine-friendlier but harder for humans to write and maintain. Markdown with frontmatter balances both needs.

Three-Level Priority Loading

Skills are loaded in priority order: project skills first, then personal skills, then built-in skills. Higher-priority skills shadow lower-priority ones with the same name, allowing customization without modifying base skills.

Alternatives: A flat skill directory would be simpler but offers no customization. The priority chain lets users override any skill without forking.
