LLM Integration

“Adapters and Streaming”

核心洞察:

The LLM layer provides message vocabulary and streaming — providers register adapters that handle the actual API calls.

LLM 层提供消息词汇和流式处理。提供者注册适配器处理实际的 API 调用，而核心循环使用统一的消息格式。

架构流程图

适配器模式

LLM 适配器模式将模型接口与实现分离。核心循环不知道它使用的是哪个提供者——它只是调用注册的适配器。

流式支持

流式处理内置于适配器模式中。每个提供者以自己的方式实现流式处理，但核心循环使用统一的流格式。

设计决策

LLM 层提供消息词汇——同一个核心循环适用于任何兼容 OpenAI 的 API。

流式处理是提供者特定的但统一消费，允许每个提供者的优化实现。

对比 Claude Code

两者都使用适配器模式，但 DeepSeek Harness 正式化了接缝。

深入设计决策

命名代理优于匿名 Worker

每个子代理有名字和文档化的专长。用户和编排器可以通过名字引用代理，建立对团队的认知模型。

备选方案: 匿名工作线程更简单，但难以推理。命名代理让系统自我文档化。

每个子代理有独立的上下文

子代理从干净的消息历史开始，只包含其任务特定的系统提示和指令。它们不继承父会话，防止上下文污染。

备选方案: 共享上下文会浪费 token 并可能因无关消息导致混淆。
